## Запуск

```bash

```

## Архитектура: Ports and Adapters (Hexagonal)

```
src/
  Pos.Domain          — ядро: сущности, VO, инварианты, Domain Service, порты репозиториев
  Pos.Application     — сценарии (PosFacade), DTO, порт IResultExporter
  Pos.Infrastructure  — адаптеры: in-memory репозитории, CsvResultExporter
  Pos.Cli             — консольный UI + composition root (DI-контейнер)
tests/Pos.Tests       — юнит-тесты
```

Стрелка зависимостей (всё направлено внутрь):

```
Pos.Cli ──► Pos.Application ──► Pos.Domain
   │                ▲                ▲
   └──► Pos.Infrastructure ──────────┘   (реализует порты из Domain и Application)
```

`Pos.Domain` не имеет ссылок ни на что (ни на проекты, ни на NuGet). Порты репозиториев лежат в домене,
порт экспорта — в приложении; адаптеры реализуют их снаружи. DI-контейнер
(`Microsoft.Extensions.DependencyInjection`) собирает граф только в `Pos.Cli/Program.cs`.

## Карта DDD

| Понятие | Где |
|---|---|
| Ubiquitous Language | `Student`, `Criterion`, `Rubric`, `Evaluation`, `Score`, `FinalGrade` — слова из ТЗ |
| Entity | `Student`, `Criterion`, `Evaluation` — у каждой есть `Id`, это «конкретный» объект, меняющийся во времени |
| Value Object | `Score` (балл), `FinalGrade` (итог) — неизменяемые `record`, равны по значению: «5 баллов» — это просто 5 баллов |
| Aggregate Root | `Rubric` — владеет критериями, снаружи критерий создать нельзя (`internal`-конструктор) |
| Инварианты | балл ≥ 0 (`Score`); балл ≤ max критерия (`Criterion.EnsureAccepts`); критерий есть в рубрикаторе (`Rubric.GetCriterion`); уникальное имя критерия, max > 0, вес > 0 |
| Repository (порт) | `IStudentRepository`, `IRubricRepository`, `IEvaluationRepository` в `Pos.Domain.Repositories`; сценарий после изменения агрегата явно сохраняет его (`Save`/`Update`), поэтому in-memory адаптер можно заменить файловым без правки фасада |
| Domain Service | `FinalGradeCalculator` — итог считается из рубрикатора и текущих оценок, нигде не хранится |

Границы агрегатов: `Rubric` (с критериями) — отдельный агрегат; `Student` и `Evaluation` — отдельные корни,
ссылаются друг на друга и на критерий только по `Id`. Правило «одна оценка на пару студент+критерий» проверяется
в сценарии `PosFacade.IssueGrade`, а исправление/отмена — отдельные операции.

## GoF-паттерны

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Factory** | `EvaluationFactory.Create` | Единственная точка создания `Evaluation`: проверяет, что критерий есть в рубрикаторе и `score ∈ [0, max]`. Конструктор `Evaluation` — `internal`, поэтому невалидную оценку создать нельзя |
| Структурный | **Facade** | `PosFacade` | Консоль не знает про репозитории, фабрику и калькулятор — вызывает один объект. Сценарии не размазаны по UI, UI легко заменить |
| Поведенческий | **Strategy** | `IFinalGradeStrategy` → `WeightedAllCriteriaStrategy`, `WeightedRatedOnlyStrategy` | Правило итога сменяемое: «all» — неоценённый критерий = 0 (финальный итог), «rated» — только оценённые (промежуточный). Переключается в меню (п. 13), `FinalGradeCalculator` не меняется |

## Допущения

- Хранилище — in-memory (данные живут, пока запущена программа); персистентность легко добавить новым адаптером к тем же портам.
- Итог выводится в процентах и по 10-балльной шкале.
- Дробные числа можно вводить и через запятую, и через точку.
- Изменение: студента можно переименовать (п. 16), оценку — исправить (п. 9; если новый комментарий не введён, сохраняется прежний).
- Ошибки ввода и нарушения инвариантов выводятся сообщением, программа не падает; при конце ввода (Ctrl+D) корректно завершается.
